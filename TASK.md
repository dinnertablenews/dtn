# Dinner Table News — scheduled run

You are the automated run for one posting slot. Do everything below without asking questions; there is no one to answer. If a step fails after two tries, write what happened to `runs/<slug>.log`, push it, and stop.

## 0. Setup
- Clone `https://github.com/dinnertablenews/dtn` and work in the clone. This scheduled task was created with the repo selected, so `git push` works; if it returns 403 "not in this session's authorized repository set", the task lost its repository binding: write that to `runs/<slug>.log` locally, make it the first line of your final message, and stop.
- Read `config.json`. If `dry_run` is true, do every step except §7.
- Determine the slot from the current time in America/Chicago: run at ~06:10 → `morning` (posts 07:00); ~11:10 → `noon` (12:00); ~19:10 → `evening` (20:00). Slug = `YYYY-MM-DD-<slot>`. If `posts/<slug>/` already exists, stop.
- Every slot builds two complete posts: the **primary** in `posts/<slug>/` and the **alternate** in `posts/<slug>-alt/`. The primary publishes unless Dan says otherwise; "alt" switches to the alternate. Both are built, rendered, and pushed to the same standard.
- Each post goes live at a random minute inside a window around its slot time, ± `publish_window_minutes` from `config.json` (10 today: noon lands between 11:50 and 12:10). The scheduled task fires 40 minutes before the window opens, so the wait from the end of the build to the latest possible target fits in one wake-up. Draw the target now, once: `python target.py <slot>` prints `{"target": ..., "seconds": ...}`. Keep the target for §6 and §7. Never draw it a second time.
- `pip install --break-system-packages feedparser requests pyyaml playwright pillow` if needed. Playwright's Chromium is preinstalled in this environment. `reel.py` also needs ffmpeg: `apt-get install -y ffmpeg` if `which ffmpeg` is empty.
- Workflow dispatches: use the GitHub MCP tool available in this session (run a workflow / `actions.createWorkflowDispatch` on `dinnertablenews/dtn`, ref `main`, with the inputs). `gh api` and `gh workflow run` return 403 in scheduled runs; don't try them.

## 1. Candidates
- `python rank.py data/headlines.json 30 > /tmp/cand.json`. Output is `{generated, window_hours, clusters: [...]}`; read the top 15 clusters.
- Read `data/log.json` (rolling record of what ran: slug, category, cluster headline, photo yes/no). Create it if missing.

## 2. Pick the story for this slot
Rules, in order:
1. Never repeat a story already in `data/log.json` from the last 7 days (same event, even if the headline moved on).
2. Same lead subject at most one slot per day. The lead subject is the person, institution, or country the headline is about (the one who would take the photo). If a slot's pick would repeat the lead subject of a post already in today's log, skip to the next cluster with a different lead subject, unless the story is the clear top story of the day: it leads the ranking by at least two outlets over the next cluster. Write the skip or the override in the log note.
3. **The positive story, every fifth.** Count back through `data/log.json` to the most recent entry whose category is "Good news". If four or more stories have run since it, or there is none in the log, this slot is the positive one: take the most uplifting cluster in the top 15 (science, rescue, record, recovery, a win) and label the category "Good news". This rule outranks 4 and 5, so the positive story lands on whichever slot comes fifth rather than on evening every day. If nothing in the top 15 qualifies, take the story 4 or 5 would have given you and label it by its real category; the count carries, so the next slot tries again. Write the count, and any carry, in the log note.
4. `morning` takes the #1 cluster of the day unless it ran yesterday evening; then #2.
5. `noon` and `evening` take the highest-ranked remaining cluster, with a tie-break for category diversity: if two clusters are within one outlet of each other, prefer the category that appears least in the last 7 days of the log.
6. Any story is fair game, including violence, abuse, suicide. That is the point of the account. Handle it with the Shield rule in §4.
7. Category is one of: Technology, Health, Economy, Government, Climate, Science, Culture, Security, World, Sports, Good news.
8. The alternate. After the primary is chosen, pick a second story for the same slot: the highest-ranked remaining cluster whose category is **not** the primary's, and which passes rules 1, 2, and 6. When rule 3 makes this slot the positive one, the alternate is the highest remaining cluster of any other category. Otherwise, if the primary is a hard story, prefer an alternate that is not. An alternate that does not run never counts as having run: it stays fair game for a later slot, and it does not count toward rule 2. Write which cluster it is and why in the log note.

## 3. Facts
- The outlets are not reachable from this environment. Read the article text from `data/articles.json` (keyed by each headline's `id`; `text` is the extracted article, `url` the resolved publisher link). Use the two or three articles in the cluster that have text. If none has text, use the RSS summaries and say so in the log. Write from what the articles say. No detail that isn't in them. Attribute the summary to the outlet whose article you leaned on most; that outlet's name goes in `outlet` and its URL in `source_url`.
- `photo_zoom`: how far into the photo the disc is cropped, default 1.0. Never ship a doubled photo. A Commons infobox image is sometimes two photographs stacked in one file (`White_House_north_and_south_sides.jpg`, artist `(top)X(bottom)Y`), and at 1.0 the disc fits both in at once, seam and all. Raise it until one of them fills the disc — about 2.1 for a half-and-half stack — never crop the picture to hide the seam some other way. The zoom crops off the bottom and the sides, never the top, so the head rule still holds, and one value frames both the cover and the reel. `render.py` fails with a `PHOTO:` line if the Commons credit names two halves and no `photo_zoom` is recorded; set it to 1.0 if the composite happens to frame well, which is the run saying it looked.
- If the story has one clear subject who is a public figure, or a landmark/spacecraft/institution, set `photo_subject` to the exact Wikipedia article title. Otherwise leave it out. Never a private individual, victim, suspect, or minor. Never on a death, arrest, or scandal about the subject. Never the same subject as any of the last three log entries. Skip the photo if the last two entries in the log both had photos. The positive story may take a photo more freely. The alternate follows the same rules, and never takes the same subject as the primary.

## 4. Write `post.json`
Same schema as `posts/samples-v2-2026-09-13-evening/post.json`. The carousel is five slides: cover, one card per age with its questions on it, and a closing dinner-table question. Write `posts/<slug>/post.json` for the primary and `posts/<slug>-alt/post.json` for the alternate; everything in this section applies to both. They share the `date` and the `cover_question` bracket (the rotation advances once per slot, not once per post). Voice and rules:
- Dan's voice and none of the AI tells. `CLAUDE.md` holds the rule in full, and it governs every word in this repository, not only `post.json`: the website, the About page, the walkthrough, the README, commit messages. Read it before writing copy and read the copy back against it afterwards.
- `date`: the posting date in America/Chicago, `YYYY-MM-DD`. The cover shows it written out ("September 13, 2026"). Never a slot or a time of day anywhere on the slides.
- Cover: `headline` ≤ 60 characters, two lines at most. `summary` 3–5 sentences, ≤ 340 characters. The summary is not on the cover; it goes in the caption.
- `cover_question`: `{"band": "<5-7|8-12|13-17>", "q": "..."}`. The cover leads with a question a kid would ask about this story, tagged with the age it comes from. Rotation: find the last entry in `data/log.json` that has a `cover_band` and take the next bracket in the order 5–7 → 8–12 → 13–17 → 5–7; if none, 5–7. The question must be one of that bracket's entries in `questions`, so its answer is on that age's card, and it must read as a question about the headline. Aim for two lines on the cover, which at its 132px is about 33 characters. There is no character cap: every cover question renders at the same 132px, and the limit is the layout, not a count. A question that crowds the age-chip row fails the render as `TOO LOW: 1-cover` — three lines fits only when the headline is one line, so with a two-line headline, keep it to two.
- `cover_age`: a whole number inside `cover_question.band` (5–7 → 5, 6, 7; 8–12 → 8–12; 13–17 → 13–17). The cover reads "So your 14-year-old asks" rather than naming the bracket. Pick it at random once, write it into `post.json`, and never redraw it: §6 re-renders after shortening text, and without the field the age would change on every pass and stop matching the notification. `render.py` draws one itself if the field is missing.
- `cover_answer`: the parent's one-line answer to the cover question, ≤ 60 characters, no hedge ("Not yet, and maybe not." / "No. Just quiet this year."). It is the first line of the caption, so under the cover in the feed the cover asks and the caption answers. It must be true to the articles.
- `source_domain`: the outlet's domain as it should read in the caption, e.g. `pbs.org/newshour`, `apnews.com`, `bbc.com`.
- `hashtags`: exactly four CamelCase tags, in this order: `#Parenting`, `#KidsAndNews`, **one** tag naming what this story is about, `#DinnerTableNews`. e.g. `["#Parenting", "#KidsAndNews", "#Congress", "#DinnerTableNews"]`. The third slot is the only free one. Make it specific — a name, place, bill, company, event. Never a category label (`#Economy`, `#Government`, `#GoodNews`, `#World`…): the cover already prints the category, so a tag that repeats it is wasted. `render.py` fails the render with a `HASHTAGS:` line if the list is the wrong length, the wrong shape, or the story tag is generic.
- Questions: 1 for 5–7, 2 for 8–12, 2 for 13–17, each with a "Try:" answer ≤ 160 characters. Real questions a kid would ask, including the awkward ones. They render on that age's card in the "They might ask" band.
- Ages 5–7: 2–4 sentences, concrete, one physical comparison, ends with reassurance or "the grown-ups have it." Open with the story, not a definition. Set `shield: true` when a parent should not raise the story unprompted (violence, death, abuse, sexual content, anything a 5-year-old can't do anything with). Then the script is what to say only if the child hears about it.
- Ages 8–12: one cause-and-effect chain they can follow, one familiar mechanism (checklist, referee, thermostat). 3–4 sentences. `chip`: "Bring it up if it fits the day" or "Good one to bring up".
- Ages 13–17: lead with a real question, then a second one. Treat them as a conversation partner. 3–4 sentences. `chip`: "Ask first, then talk".
- `why` lines: one or two sentences on why this works at that age, in plain language. **Where the card has room, add one more sentence naming the developmental reason** — what a child of that age can and cannot yet do that makes this the right way in. Tie it to this story's advice, never a general fact about the age. Room is the constraint and the render decides it: add the sentence, re-render, and if `TOO LOW` fires on that card, cut it back or drop it. Never shorten the script to make space for it — the script is the product, this is the reason behind it.
- `why_long`: the same line written for the website, where nothing is measured and there is room to say it properly. One per age, on every post, and never longer than that post's `summary` — the reader came for the news, so the note about how to talk about it is the smaller of the two. `site.py` fails the build with a `WHY TOO LONG:` line naming the post, the band and the overage; cut until it passes, the way you cut for `TOO LOW`. The site renders this in place of `why`; the Instagram card never sees it, so writing it can never make a slide fail the render. What it has to do: name the developmental mechanism this story runs into, and show the script answering it. Ground it in how children actually develop — a five-year-old reasons from what is in front of them, takes one vivid feature for the whole event and reads a parent's face before the words; an eight-to-twelve-year-old is working out chains of cause and effect, rules, fairness and whether adults apply them consistently; a teenager can hold two true things at once, reason about what is not in front of them, and is testing whether you will argue honestly. Where a researcher earns the sentence, name them: Piaget for what a stage can and cannot do, Vygotsky for why the words go to the adult, Cantor for what frightens a child at each age, Kuhn for argument as a skill that is practised. Do not name one every time — three posts in a row opening on Piaget reads as a template, and the mechanism matters more than the citation. It must be about THIS story: which detail in the script is the concrete anchor, which chain the child is being handed, which two things the teenager is being asked to hold. A `why_long` that would fit any story that week is not finished. It also says what to expect next — the question this age reliably asks after this kind of story, and the honest answer to it. Read it back against the tell list in `CLAUDE.md` before you commit it. The triad is the one that catches people here: three parallel clauses about what an age can do is a rule-of-three, however true each clause is.
- `table_question`: one question anyone at the table can answer without knowing the news, drawn from the story's tension (a rule, a choice, a fairness call). ≤ 70 characters. It is the last slide and the comment prompt.
- `caption`: do not write it. Leave the field out; `render.py` builds it from the fields above and writes it into `post.json` on the first render. The order is fixed: `cover_answer`, the summary, "Source: <outlet>, <source_domain>" with the photo credit line under it if a photo ran, "Swipe for what to say at 5, at 10, and at 15.", "The dinner table question: <table_question> Tell us what your kid said, and how old they are.", the hashtags. If you change a field after the first render, delete `caption` and render again; a caption that doesn't match its fields fails the render with a `CAPTION:` line.

## 6. Render and push
- `python render.py posts/<slug>/post.json posts/<slug>/`
- `render.py` measures every slide and exits non-zero with a `TOO LOW:` line naming the slide when text sits too close to what follows it: on each age card at least 72px of paper between the "Why it works" line and the "They might ask" band, and the band must end inside the card; on the cover the question must clear the age-chip row; on the table slide the comment line must clear the save/send/follow block. Shorten the text it names (the script, the why line, a Try answer, the question) and re-render until it exits 0. Never commit or publish a post whose render fails this check, and never work around it by changing sizes or the check itself; the three age cards must match.
- Look at the five JPGs (Read them). Fix anything that overflows or wraps badly by shortening text, then re-render. Cover headline two lines at most; cover question two lines at most. Count lines in the image before telling Dan how many there are.
- Do all of the above for both folders. Both renders must exit 0; look at all ten JPGs.
- `python reel.py posts/<slug>/post.json posts/<slug>/` for the PRIMARY only. It writes `reel.mp4` (20.5s vertical), `reel-cover.jpg` and `reel-caption.txt` from the same `post.json`, so there is nothing to write. The caption is the post's own, minus the swipe line: a reel has nothing to swipe and has already played the three ages by the time anyone reads it. It takes about 80 seconds. **Look at `reel-cover.jpg`** when the post has a photo: the reel's disc is fully on-frame and taller than the cover's, so it can show things the cover crops away.
- The reel is optional cargo: Dan posts it by hand and picks the music. If `reel.py` fails for any reason, note it in the log and carry on — a reel must never delay or block the carousel, which is what actually publishes.
- The reel is built for the primary because that is what publishes unless Dan says otherwise. If he replies `alt`, §7 rebuilds it for the alternate and deletes the primary's: exactly one reel per slot, and it is always the post that ran.
- Append one entry to `data/log.json` for the slot: the primary's `category`, `headline`, `photo`, `cover_band`, `publish_target` (the drawn target), `chosen: "primary"`, and `alternate: {"folder": "posts/<slug>-alt", "category": ..., "headline": ..., "photo": true|false}`. Commit `posts/<slug>/` (including `reel.mp4`, `reel-cover.jpg` and `reel-caption.txt`), `posts/<slug>-alt/`, and `data/log.json`, push to `main`.
- Write the summary for the notification, five lines: "Primary: <headline>", "Alternate: <headline>", the target time ("Posts at 11:57 CT"), and the two reel links so Dan can save them from his phone:
  `https://raw.githubusercontent.com/dinnertablenews/dtn/main/posts/<slug>/reel.mp4`
  `https://raw.githubusercontent.com/dinnertablenews/dtn/main/posts/<slug>/reel-cover.jpg`
  Say "no reel" on that line instead if `reel.py` failed. It reaches Dan's phone when this run's turn ends.
- Under those five lines, paste the reel caption: the full text of `posts/<slug>/reel-caption.txt`, verbatim, in a fenced code block so it copies clean on a phone. Dan posts the reel by hand and needs the caption in the same thread as the links, every slot, without asking. Whenever the reel is rebuilt later in the thread (an edit, or the alternate taking over), paste the new caption again with the new links.

## 7. Publish window (skipped when `dry_run` is true)
The timer lives in GitHub Actions, not in this session. A session wake-up armed for the target failed to fire on 2026-09-14 (noon and evening), so nothing about whether the post goes out may depend on one. The veto is a file on `main`.
- Right after the §6 push, dispatch `publish.yml` via the GitHub MCP tool with inputs `action=publish`, `folder=posts/<slug>`, `publish_at=<the target from §0 as ISO 8601 with offset, e.g. 2026-09-14T20:00-05:00>`, ref `main`. The workflow sleeps until `publish_at`, pulls `main`, and publishes unless `posts/<slug>/HOLD` exists. It commits the permalink to `published.json` and into the slot's `data/log.json` entry itself. If the target has already passed when the build finishes, omit `publish_at`: it publishes at once. Say so in the summary.
- Find the run you just queued (`actions_list`, `list_workflow_runs`, `publish.yml`: the newest `workflow_dispatch` run) and record its id in the log entry as `publish_run`; push.
- END YOUR TURN with the summary from §6, the reel caption included, plus "Reply kill, skip, or hold to stop it, or alt to run the alternate instead." Ending the turn is what pings Dan. Before ending, if `ScheduleWakeup` is available, arm it for the target plus 180 seconds as a best-effort ping only: when it fires, `git pull`, read `published.json`, and send Dan the headline and permalink. If it never fires, nothing is lost; the workflow has already logged the permalink.
- Dan's replies wake this session. Handle each one, then end the turn again. Everything below is pushed to `main` before the target, because `main` is what the workflow reads:
  - **kill / skip / hold**: write `posts/<slug>/HOLD` (one line: the word and the time), commit, push to `main`. Then cancel the run too (`actions_run_trigger`, `cancel_workflow_run`, the `publish_run` id). Set `chosen: "none"` and note it in the log entry, push. Nothing publishes.
  - **alt / alternate / the alternate's headline**: write `posts/<slug>/HOLD`, push, cancel the primary run, then dispatch `publish.yml` with `folder=posts/<slug>-alt` and the same `publish_at` (omit it if the target has passed). Record the new run id as `publish_run`, push. `publish.py` sets `chosen: "alternate"` when it publishes.
    Then move the reel across, **after** that dispatch is recorded and never before it: run `python reel.py posts/<slug>-alt/post.json posts/<slug>-alt/`, delete `posts/<slug>/reel.mp4`, `posts/<slug>/reel-cover.jpg` and `posts/<slug>/reel-caption.txt`, commit and push. The reel that exists is the post that ran: never leave the primary's reel behind when the alternate publishes, or Dan posts a reel for a story the account never carried. Give Dan the new links (`posts/<slug>-alt/reel.mp4` and `reel-cover.jpg`) and paste the new `reel-caption.txt` in full when you end the turn. Still optional cargo: if `reel.py` fails, delete the primary's three files anyway, say "no reel", and carry on — the alternate's carousel is already dispatched and must not wait on a reel.
  - **An edit** to either post: apply it, delete `caption`, re-render until exit 0, look at the JPGs, commit, push to `main`. If the edit changed the headline, the cover question, or a `Try:` answer on the post that is going to publish, its reel is now stale: re-run `reel.py` on that folder and push it too, after the carousel push has landed. The workflow pulls right before publishing, so a push that lands at least two minutes before the target is what goes out. Later than that: write HOLD, cancel the run, push the edit with HOLD removed, and dispatch again (omit `publish_at` if the target has passed).
  - **A swap to a third story**: rebuild the primary folder in place (§3–6), then the same push-or-redispatch rule as an edit.
  - **A question**: answer it. Nothing else changes.
- If the dispatch fails twice, write `runs/<slug>.log`, push it, say so in the summary, and stop. Nothing publishes.
- Never `sleep` in this session to wait for the target, and never treat a session wake-up as the thing that publishes.

## Guardrails
- Sources are only the outlets in `feeds.yaml`. Never introduce another.
- Never invent a quote, number, or name. If the articles don't say it, the post doesn't say it.
- If the top story is something you cannot write responsibly for kids at all (e.g., detailed sexual violence with no way to frame it), pick the next story and note why in the log. This should be rare; the Shield exists for hard stories.
